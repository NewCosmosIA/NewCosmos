1. Finalidade

Objetivo do manual

Este documento serve como uma regra operacional para qualquer IA conectada a um projeto de software. A IA deve usá-lo para criar projetos completos, bem separados por responsabilidade, com código legível, documentação, testes, pipeline de validação e fluxo seguro de versionamento.

Resultado esperado: ao receber uma ideia de projeto, a IA deve conseguir transformar essa ideia em um repositório organizado, com arquitetura clara, padrões de código, módulos bem definidos, documentação mínima, testes e preparação para evolução contínua.

O que este manual resolve

Evita projeto bagunçado

Impede arquivos gigantes, pastas genéricas, duplicidade de funções, mistura de regra de negócio com interface e alterações sem controle.

Cria uma base escalável

Define uma estrutura onde novas features entram em módulos próprios, com testes e documentação desde o início.

Melhora o trabalho da IA

Arquivos menores, nomes claros e mapas de feature tornam o contexto mais fácil de interpretar e reduzem erros de implementação.

Protege a branch principal

Todo trabalho deve acontecer em branches próprias, com revisão por diff e pull request antes de chegar à versão principal.

Força qualidade

Código novo deve ser acompanhado por testes, lint, typecheck, build e validações automáticas.

Cria documentação viva

A IA deve registrar arquitetura, decisões, mapa de funcionalidades, contratos de API, estratégia de testes e regras de evolução.

2. Aplicação prática

Como usar este relatório com uma IA

Este documento pode ser usado de três formas:

UsoQuando aplicarComo a IA deve agir
Criação do zero Quando o projeto ainda não existe. A IA cria estrutura, documentação, arquitetura, configurações, módulos iniciais, testes e pipeline.
Projeto existente Quando já existe um repositório com código. A IA primeiro audita o projeto, entende a arquitetura, cria branch e só depois altera o necessário. Fluxo completo em projetos existentes e legados.
Padronização contínua Quando várias conversas, agentes ou pessoas vão trabalhar no mesmo sistema. A IA usa as mesmas regras para toda tarefa: escopo pequeno, sem duplicidade, testes, diff e PR.

Regra de execução

A IA não deve começar escrevendo código imediatamente. Primeiro ela deve entender o objetivo, propor a arquitetura, criar a base do repositório, definir os documentos de controle e só então implementar as features.

Importante: quando o pedido do usuário for incompleto, a IA não deve travar. Ela deve assumir padrões seguros, registrar as decisões tomadas e continuar com uma primeira versão funcional e bem organizada.
3. Regras centrais

Princípios obrigatórios de qualquer projeto

Estes princípios são a base do padrão. Eles devem ser respeitados independentemente da linguagem, framework, banco de dados ou tipo de aplicação.

1. Uma responsabilidade por arquivo

Cada arquivo deve ter um motivo claro para existir. Um arquivo não deve misturar interface, regra de negócio, acesso a banco, validação, configuração e teste.

2. Uma feature por módulo

Funcionalidades devem ser agrupadas por domínio ou feature, e não espalhadas em pastas genéricas sem contexto.

3. Não duplicar funcionalidade

Antes de criar uma função, tela, endpoint, service, componente ou tabela, a IA deve procurar se já existe algo igual ou parecido.

4. Código novo exige teste

Toda regra de negócio nova ou alterada deve ter teste. Correção de bug deve vir acompanhada de teste que prove a correção.

5. Branch principal protegida

A branch principal deve receber mudanças apenas por pull request, revisão de diff e validação automática.

6. Documentação acompanha código

Quando a IA cria ou altera uma feature, a documentação de arquitetura, feature map, API e decisões deve ser atualizada.

Resumo executivo das regras

REGRA 1: Não trabalhar direto na main.
REGRA 2: Criar branch por tarefa ou módulo.
REGRA 3: Planejar antes de codar.
REGRA 4: Procurar antes de criar para evitar duplicidade.
REGRA 5: Manter arquivos pequenos e coesos.
REGRA 6: Separar controller, service, repository, validators, types e tests.
REGRA 7: Testar regra de negócio nova ou alterada.
REGRA 8: Rodar lint, typecheck, testes e build.
REGRA 9: Revisar o diff antes de concluir.
REGRA 10: Atualizar documentação junto com o código.
4. Comportamento esperado

Papel da IA dentro do projeto

A IA deve atuar como uma equipe técnica completa. Ela não deve apenas gerar código: deve coordenar, organizar, revisar, testar e documentar.

PapelResponsabilidadeResultado esperado
Arquiteta Define camadas, módulos, limites de responsabilidade, padrões e estrutura de pastas. Projeto nasce organizado e pronto para crescer.
Coordenadora técnica Divide trabalho por branches, features, tarefas e PRs pequenos. Alterações rastreáveis, sem conflito e sem bagunça.
Desenvolvedora Implementa código limpo, pequeno, tipado quando possível e aderente ao padrão. Funcionalidades funcionando com baixo acoplamento.
Revisora Analisa diff, risco, duplicidade, nomes, responsabilidades, testes e impacto. Menos regressões e mudanças fora de escopo.
QA automatizado Cria testes unitários, integração, e2e quando necessário e valida cobertura. Erros são encontrados antes do deploy.
DevOps Configura CI/CD, variáveis de ambiente, build, deploy e gates de qualidade. Pipeline confiável para publicar com segurança.
Documentadora Mantém README, arquitetura, decisões, mapa de features e guias operacionais. O projeto permanece compreensível para humanos e IAs.
Mandamento operacional: a IA deve sempre entregar uma base que outro desenvolvedor ou outra IA consiga continuar sem precisar adivinhar a arquitetura.
5. Informações iniciais

Entrada mínima para criar qualquer projeto

Quando receber uma ideia, a IA deve transformar a ideia em especificação. Mesmo quando o usuário não fornecer todos os detalhes, a IA deve criar uma base racional e registrar as suposições.

Dados que a IA deve coletar ou inferir

CategoriaPerguntaSe não houver resposta

Usuários Quem usa o sistema? Criar personas iniciais: administrador, usuário comum e operador.
Tipo de produto Web app, API, mobile, automação, dashboard, SaaS, CLI, agente de IA? Escolher arquitetura modular compatível com o pedido.
Stack Qual tecnologia deve ser usada? Propor stack padrão e documentar a escolha.
Banco Precisa persistir dados? Se houver usuários, transações ou histórico, incluir banco e migrations.
Autenticação Precisa login, permissões e papéis? Incluir autenticação quando houver dados privados ou área administrativa.
Deploy Onde será publicado? Criar pipeline genérico e documentar opções.
Qualidade Qual cobertura de testes mínima? Adotar baseline inicial e meta de crescimento, com testes para código novo.

6. Processo principal

Fluxo para a IA criar um projeto do zero

A IA deve executar o projeto em fases. Cada fase produz arquivos, decisões e validações. O objetivo é impedir que o projeto nasça como um bloco de código improvisado.

Entender a ideia e criar o brief

Converter o pedido em objetivo, escopo, usuários, funcionalidades, restrições e premissas. Criar docs/PROJECT_BRIEF.md.

Escolher arquitetura e stack

Definir camadas, tecnologias, banco, autenticação, testes e deploy. Registrar decisões em docs/ARCHITECTURE.md e docs/DECISIONS/.

Criar repositório e branch inicial

Inicializar Git, criar branch init/project-foundation, adicionar .gitignore, .editorconfig, README, docs e configurações.

Criar estrutura modular

Montar pastas por domínio/feature, separar shared, config, tests, docs, scripts e .github/workflows.

Implementar fundação técnica

Configurar ambiente, validação, logger, tratamento de erro, conexão com banco, roteamento, layout base, autenticação se necessário e padrões de resposta.

Implementar features em ciclos pequenos

Cada feature deve ter especificação, arquivos próprios, testes, atualização do mapa de features e PR separado.

Configurar qualidade automática

Adicionar lint, formatação, typecheck, testes, cobertura, build e pipeline de CI/CD.

Revisar diff e preparar pull request

Conferir alterações contra a branch principal, explicar impacto, riscos, testes e documentação atualizada.

Entregar versão executável

O projeto deve rodar localmente, ter instruções claras, testes passando e caminho de deploy definido.

7. Projetos existentes e legados

Adotar o manual em um projeto que já está rodando

Este manual foi pensado principalmente para projetos novos, onde tudo nasce organizado. Mas a maioria das pessoas já tem um projeto em andamento, com muita coisa acontecendo. Esta é a trilha para esse caso: aqui o primeiro passo não é codar, é contextualizar o que já existe.

Atenção: em um projeto existente, começar a alterar código sem antes mapear e documentar é receita para duplicar funcionalidade e quebrar o que já funciona. Quem tem experiência improvisa; quem está começando se perde. Por isso esta seção existe.

Novo x existente: qual trilha seguir

Projeto novo (Trilha A)
  • Comece pelo fluxo do zero.
  • Estrutura, docs e testes nascem junto com o código.
  • Convenções aplicadas desde o primeiro arquivo.
Projeto existente (Trilha B)
  • Primeiro mapeie e documente o que já existe.
  • Segregue a documentação por feature retroativamente.
  • Adote branches, testes e CI/CD de forma gradual.

Fluxo para adotar o padrão em um projeto existente

Mapear o que já existe

Peça à IA para varrer o repositório e produzir um mapa: features atuais, módulos, pontos de entrada, dependências e onde estão as maiores dores (arquivos grandes, duplicidade, áreas sem teste).

Gerar documentação por feature retroativa

Para cada feature já existente, crie o pacote de documentação por feature (README, contexto, contrato de API, instruções). Isso dá à IA o contexto que faltava para trabalhar sem quebrar nada.

Identificar e resolver duplicidade

Antes de criar qualquer coisa nova, procure se já existe. Consolide funcionalidades repetidas e registre o que foi unificado.

Introduzir testes de caracterização

Em código legado sem testes, escreva testes que capturam o comportamento atual antes de mudar. Eles viram a rede de segurança contra regressão.

Adotar branches, PR e CI/CD gradualmente

Passe a trabalhar em branches fora da principal, com merge por diff e pull request. Ligue lint, typecheck e testes no CI aos poucos, começando pelas áreas mais críticas.

Ligar observabilidade

Configure monitoramento e crash analytics (observabilidade) para acompanhar a saúde do sistema enquanto ele evolui.

Definição de pronto (projeto existente): o que existia está mapeado e documentado por feature, duplicidades conhecidas foram resolvidas, mudanças passaram a acontecer em branch com testes, e o sistema tem monitoramento mínimo — sem precisar reescrever tudo de uma vez.

Prompt para adotar o padrão em um projeto existente

Assuma este projeto EXISTENTE como arquiteto e coordenador. Não altere
comportamento ainda. Primeiro:
1. Mapeie o repositório: features, módulos, pontos de entrada, dependências
   e maiores dores (arquivos grandes, duplicidade, áreas sem teste).
2. Para cada feature existente, crie documentação segregada dentro da própria
   feature: README, contexto, contrato de API e instructions.
3. Aponte duplicidades de funcionalidade e proponha consolidação.
4. Sugira testes de caracterização para o comportamento atual antes de mudanças.
5. Proponha um plano gradual de branches, pull request por diff e CI/CD.
6. Proponha observabilidade mínima (métricas/alertas no backend, crash
   analytics no app) para acompanhar a saúde do sistema.
Entregue o mapa e o plano antes de escrever qualquer código novo.

Regras para nomear pastas

PastaUso corretoEvitar
features/ Funcionalidades de domínio: users, companies, billing, reports. Colocar utilitários globais ou configurações.
shared/ Código reutilizado por várias features. Virar depósito de qualquer coisa sem dono.

tests/ Testes globais, integração, e2e, fixtures. Testes unitários de feature longe da feature sem motivo.
9. Documentação viva

Documentos obrigatórios do projeto

Um projeto bem organizado precisa explicar sua própria estrutura. A IA deve criar e manter estes documentos desde o início.

DocumentoFunçãoAtualizar quando
README.md Explica o projeto, instalação, execução, testes e comandos principais. Sempre que mudar setup, scripts, arquitetura ou uso.
docs/PROJECT_BRIEF.md Define objetivo, escopo, usuários, premissas e riscos. Quando o escopo de produto mudar.
docs/AI_PROJECT_RULES.md Regras que toda IA deve seguir ao mexer no projeto. Quando padrões de trabalho mudarem.
docs/ARCHITECTURE.md Descreve camadas, módulos, fluxo de dados e decisões técnicas. Quando criar módulo, integração ou mudar arquitetura.
docs/FEATURE_MAP.md Mapa de funcionalidades existentes para evitar duplicidade. A cada feature criada, alterada ou removida.
docs/API_CONTRACT.md Contratos de endpoints, payloads, respostas e erros. Quando API mudar.
docs/DATABASE.md Modelo de dados, tabelas, relacionamentos e migrations. Quando banco mudar.
docs/TEST_STRATEGY.md Política de testes, cobertura e comandos. Quando criar novo tipo de teste ou mudar meta.
docs/DEPLOYMENT.md Como publicar, ambientes, variáveis e rollback. Quando pipeline ou deploy mudar.
docs/DECISIONS/ Registra decisões arquiteturais importantes. Quando uma escolha técnica impactar o projeto.

Regra de documentação

Código sem documentação mínima não está completo. A IA deve registrar o que foi criado, por que foi criado, onde está, como testar e como evoluir.

Em projetos grandes, estes documentos não devem viver apenas na raiz: cada feature deve carregar seu próprio pacote de documentação. Veja documentação por feature.

10. Documentação por feature

Documentação segregada: um conjunto de docs por feature

Em projetos grandes, uma documentação geral única vira um bloco difícil de manter e de ler. O padrão superior é segregar: cada feature carrega a sua própria documentação, o seu contrato de API e as suas instruções, ao lado do próprio código.

Ideia central: quando uma IA vai mexer em uma parte do sistema, ela deve encontrar ali mesmo, dentro da feature, todo o contexto de que precisa — sem ter que varrer uma documentação global gigante para achar o pedaço certo.

Global x por feature

Documentação só global
  • Tudo empilhado em docs/ na raiz.
  • A IA lê muito para achar pouco contexto útil.
  • Fácil ficar desatualizada e desconectada do código.
  • Escala mal em projetos grandes.
Documentação por feature
  • Cada feature tem o seu próprio contexto ao lado do código.
  • A IA lê apenas o documento da feature que vai tocar.
  • Atualizar a feature e atualizar o doc andam juntos.
  • Escala bem: novas features chegam autoexplicadas.

Estrutura de exemplo

Exemplos reais de um e-commerce: as features carrinho e busca, cada uma com todo o seu contexto documentado para as IAs lerem quando forem mexer nelas.

src/features/
├─ carrinho/
│  ├─ docs/
│  │  ├─ README.md            # o que a feature faz e como usar
│  │  ├─ contexto.md          # regras de negócio e decisões
│  │  ├─ api-contract.md      # contrato de API da feature
│  │  └─ instructions.md      # instruções para a IA ao editar
│  ├─ components/
│  ├─ services/
│  └─ tests/
└─ busca/
   ├─ docs/
   │  ├─ README.md
   │  ├─ contexto.md
   │  ├─ api-contract.md
   │  └─ instructions.md
   ├─ components/
   ├─ services/
   └─ tests/
Regra prática: os documentos que o manual manda criar (README, contrato de API, instruções, contexto) não precisam viver só na raiz. Em projetos grandes, crie-os dentro de cada feature. Mantenha na raiz apenas o que é realmente transversal ao projeto inteiro.
11. Design modular

Arquitetura por features

O padrão recomendado é organizar o projeto por funcionalidades. Isso evita que o código fique espalhado em pastas genéricas e facilita o trabalho de qualquer IA ou desenvolvedor.

Modelo de uma feature completa

src/features/users/
  users.controller.ts      # Entrada: rotas, request, response
  users.service.ts         # Regras de negócio
  users.repository.ts      # Banco ou persistência
  users.validators.ts      # Validação de entrada
  users.types.ts           # Tipos e interfaces
  users.constants.ts       # Constantes da feature
  users.mapper.ts          # Conversão de entidades/DTOs
  users.events.ts          # Eventos gerados pela feature, se existir
  users.test.ts            # Testes unitários principais
  users.integration.test.ts# Testes de integração, se necessário
  index.ts                 # Exportações controladas

Responsabilidades por camada

CamadaPode fazerNão pode fazer
Controller / Route Receber entrada, chamar validação, chamar service, retornar resposta. Conter regra de negócio pesada ou query direta no banco.
Service / Use Case Executar regra de negócio, orquestrar repositórios, validar fluxo. Depender diretamente de UI ou detalhes de HTTP.
Repository / Gateway Isolar acesso ao banco, API externa ou storage. Conter regra de negócio que deveria estar no service.
Validators Validar formato, obrigatoriedade, tipos e limites de entrada. Executar operação de banco ou regra de domínio complexa.
Types / DTOs Definir contratos internos e externos. Executar lógica.
Tests Provar comportamento, erros, bordas e regressões. Ser apenas teste superficial sem assert relevante.

Quando mover algo para shared

Um código só deve ir para shared quando for usado por duas ou mais features ou quando for claramente infraestrutura do sistema. Não coloque uma função em shared apenas porque não sabe onde ela pertence.

Vai para shared

  • Logger global.
  • Cliente de banco.
  • Tratamento de erro comum.
  • Validador genérico reutilizado.
  • Tipos globais realmente compartilhados.
  • Funções utilitárias usadas por várias features.

Não deve ir para shared

  • Regra específica de uma feature.
  • Componente usado em uma única tela.
  • Query específica de um módulo.
  • Código sem dono claro.
  • Arquivos genéricos como helpers.ts com várias responsabilidades.
12. Tamanho e clareza

Regra operacional dos 200 linhas

O limite de 200 linhas não é uma lei matemática. É um alerta de arquitetura. Quando um arquivo cresce demais, a IA deve verificar se ele está acumulando responsabilidades.

Tamanho do arquivoStatusAção obrigatória
Até 120 linhas Saudável Manter se estiver coeso.
121 a 200 linhas Atenção Revisar se há mistura de responsabilidades.
201 a 250 linhas Alerta Fragmentar ou justificar claramente.
251 a 400 linhas Risco Refatorar por função, feature ou camada.
Acima de 400 linhas Crítico Tratar como dívida arquitetural, exceto arquivo gerado ou caso justificado.

Perguntas que a IA deve fazer ao encontrar arquivo grande

  • Este arquivo tem mais de uma responsabilidade?
  • Existe regra de negócio misturada com interface?
  • Existe validação misturada com acesso ao banco?
  • Existem constantes, tipos e helpers que poderiam estar separados?
  • Há funções independentes que deveriam virar módulos próprios?
  • Existe código duplicado dentro do próprio arquivo?
  • O nome do arquivo ainda representa todo o conteúdo?
  • Os testes ficam difíceis porque o arquivo faz coisas demais?

Exceções permitidas

Alguns arquivos podem passar de 200 linhas, mas precisam de justificativa:

Tipo de arquivoPode passar?Condição

Arquivos geradosSimQuando não devem ser editados manualmente.
DocumentaçãoSimQuando a leitura ainda estiver organizada por seções.
Testes extensosSim, com cuidadoQuando muitos cenários pertencem à mesma unidade testada.

13. Versionamento seguro

Git, branches, pull request e merge por diff

O projeto deve ser versionado desde o início. A branch principal representa a versão estável. Toda alteração relevante deve acontecer em uma branch separada e ser enviada por pull request.

Branches recomendadas

TipoPadrãoExemplo
Fundaçãoinit/<nome>init/project-foundation
Featurefeature/<nome>feature/user-authentication
Correçãofix/<nome>fix/login-validation-error
Refatoraçãorefactor/<nome>refactor/users-service-split
Testetest/<nome>test/billing-rules
Documentaçãodocs/<nome>docs/api-contract
Infrachore/<nome>chore/setup-ci

Comandos base

# iniciar projeto
mkdir <project-name>
cd <project-name>
git init

# criar branch inicial
git checkout -b init/project-foundation

# ver alterações
git status
git diff

# commit
git add .
git commit -m "init: create project foundation"

# criar nova branch para feature
git checkout main
git pull origin main
git checkout -b feature/<feature-name>

# revisar diff antes do PR
git diff main...HEAD

Worktrees: várias frentes de trabalho no mesmo repositório

Um mesmo repositório pode manter vários worktrees: cópias de trabalho simultâneas, cada uma apontando para uma branch diferente. Isso permite que várias frentes — conversas de IA, agentes ou squads — trabalhem ao mesmo tempo em partes diferentes do sistema sem uma sobrescrever a outra e sem ficar trocando de branch na mesma pasta.

# criar um worktree novo em outra pasta, já em uma branch própria
git worktree add ../<project>-frontend feature/frontend-checkout
git worktree add ../<project>-backend feature/backend-checkout

# listar worktrees ativos
git worktree list

# remover worktree ao concluir a frente de trabalho
git worktree remove ../<project>-frontend

Regras para trabalho paralelo com múltiplas frentes

  • Uma branch por frente de trabalho: cada squad, agente ou conversa de IA atua em uma branch própria por setor importante do sistema (ex.: feature/frontend-busca, feature/backend-busca).
  • Um worktree por frente ativa: frentes simultâneas não devem compartilhar a mesma cópia de trabalho.
  • Cada frente integra suas mudanças pela branch principal via pull request com merge por diff — nunca copiando o projeto inteiro por cima.
  • Antes de abrir uma frente nova, verificar no feature map se outra frente já cobre o mesmo escopo, para não duplicar trabalho.
  • Frentes que tocam os mesmos arquivos devem ser sequenciadas ou coordenadas, não executadas em paralelo às cegas.

Regra de merge por diff

O merge deve considerar apenas o que foi alterado pela branch. A IA não deve substituir pastas inteiras, recriar projeto por cima do existente nem sobrescrever mudanças de outras frentes de trabalho.

Proibido: copiar o projeto inteiro novamente para dentro da branch principal quando a tarefa alterou apenas alguns arquivos. Isso causa perda de código, conflito e duplicidade.

Política de pull request

  • Um PR deve ter um objetivo claro.
  • Um PR deve ter escopo pequeno.
  • Um PR deve explicar arquivos alterados e motivo.
  • Um PR deve listar testes executados.
  • Um PR deve indicar se documentação foi atualizada.
  • Um PR deve informar se algum arquivo passou do limite recomendado.
  • Um PR não deve misturar feature, refatoração ampla e mudança de infraestrutura sem necessidade.

15. Garantia contra regressão

Testes e cobertura

Teste não é opcional. A IA deve considerar teste como parte da implementação. O objetivo é detectar erro cedo, permitir refatoração segura e evitar que uma mudança quebre outra parte do sistema.

Tipos de teste

TipoO que testaQuando usar
Unitário Função, regra ou service isolado. Obrigatório para regra de negócio.
Integração Comunicação entre módulos, banco, API interna. Quando o valor depende de interação entre camadas.
E2E Fluxo completo como usuário real. Para fluxos críticos: login, pagamento, cadastro, checkout, geração de relatório.
Contrato Entrada e saída de APIs, eventos ou integrações. Quando há frontend/backend separados ou integrações externas.
Smoke Se a aplicação sobe e fluxos mínimos funcionam. Após deploy ou build.
Regressão Bug corrigido para garantir que não volte. Sempre que corrigir bug.

Política de cobertura

CenárioMeta recomendadaRegra
Projeto novo Alta cobertura desde o início. Código de regra de negócio novo deve ter teste.
Projeto legado Baseline atual + crescimento gradual. Não permitir queda de cobertura.
Fluxo crítico Cobertura forte com unitário + integração ou e2e. Não publicar sem teste.
Bug corrigido Teste de regressão obrigatório. O teste deve falhar antes da correção ou comprovar o caso corrigido.

Checklist de teste para IA

- [ ] Existe teste para o fluxo principal?
- [ ] Existe teste para entrada inválida?
- [ ] Existe teste para ausência de permissão?
- [ ] Existe teste para recurso inexistente?
- [ ] Existe teste para regra de negócio crítica?
- [ ] Existe teste para erro esperado?
- [ ] Existe teste para bug corrigido?
- [ ] Os testes não dependem de ordem de execução?
- [ ] Os mocks são claros e mínimos?
- [ ] A cobertura não caiu?

Higiene de processos: watchers e workers órfãos

Test runners paralelos (vitest, jest e similares) abrem cerca de um worker por núcleo da máquina. Se o processo pai morre sem encerramento limpo — terminal fechado sem Ctrl+C, editor finalizado à força, sessão de IA interrompida — os workers filhos não recebem o sinal de parada, viram órfãos (adotados pelo init, PPID=1) e continuam girando CPU indefinidamente, invisíveis em qualquer terminal. O sintoma é máquina lenta e load average muito acima do número de núcleos.

Regra para a IA: todo processo iniciado durante uma tarefa (test runner, watcher, dev server, worker) deve ser encerrado ao concluir a tarefa. Em automações e CI, prefira execução única (run) em vez de modo watch — watch é para uso interativo de humanos.

Diagnóstico e limpeza de órfãos

# top consumidores de CPU
ps -Ao pid,ppid,pcpu,pmem,comm -r | head -16

# load average (comparar com o nº de núcleos)
uptime            # núcleos: sysctl -n hw.ncpu (macOS) | nproc (Linux)

# localizar workers órfãos (PPID=1 = sem processo pai vivo)
ps -Ao pid,ppid,command | awk '$2==1 && /vitest|jest|node/ {print}'

# encerrar SOMENTE os órfãos (TERM primeiro, -9 nos teimosos)
ps -Ao pid,ppid,command | awk '$2==1 && /vitest/ {print $1}' | xargs kill -TERM
sleep 2
ps -Ao pid,ppid,command | awk '$2==1 && /vitest/ {print $1}' | xargs kill -9 2>/dev/null
Cuidado: matar apenas processos com PPID=1. Um teste rodando de verdade tem processo pai vivo e nunca deve ser morto por script — nesses casos, encerre com Ctrl+C no terminal dono. Evite pkill -f genérico, que derruba também execuções legítimas de outras frentes de trabalho.
16. Automação de validação

Pipeline de CI/CD

CI/CD é a esteira automática que valida o projeto antes de aceitar alterações e, quando configurado, publica em ambientes de teste ou produção. A IA deve criar um pipeline mínimo logo no início.

Pipeline mínimo recomendado

Checkout

Baixar o código da branch.

Instalar dependências

Instalar pacotes com lockfile respeitado.

Lint

Verificar padrão de código.

Formatação

Validar estilo quando houver ferramenta de formatter.

Typecheck

Validar tipos em linguagens ou stacks tipadas.

Testes

Rodar unitários e integração conforme necessário.

Cobertura

Verificar se a cobertura mínima foi mantida.

Build

Gerar versão final e provar que compila.

Auditoria básica

Checar segredos, arquivos grandes, dependências e duplicidade.

Deploy

Publicar em staging e depois produção, quando configurado.

Exemplo genérico de workflow

name: CI

  pull_request:

  push:

  validate:

      - name: Setup runtime
        run: echo "Configure aqui Node, Python, Java, Go ou a stack do projeto"

      - name: Install dependencies
        run: echo "Instale dependências com o gerenciador correto"

      - name: Lint
        run: echo "Rodar lint"

      - name: Typecheck
        run: echo "Rodar typecheck se aplicável"

      - name: Tests
        run: echo "Rodar testes"

      - name: Coverage
        run: echo "Validar cobertura"

      - name: Build
        run: echo "Rodar build"

      - name: File size check
        run: echo "Verificar arquivos grandes e exigir justificativa"

Gates que bloqueiam merge

  • Testes falhando.
  • Build falhando.
  • Lint ou typecheck falhando.
  • Cobertura caindo sem justificativa.
  • Arquivo grande sem justificativa.
  • Segredo ou chave no código.
  • Duplicidade evidente de módulo ou função.
  • Alteração fora do escopo do PR.

A validação não termina no deploy: depois de publicar, a saúde do sistema deve ser acompanhada por observabilidade e monitoramento.

17. Observabilidade e monitoramento

Observabilidade: acompanhar a saúde do sistema em produção

Um projeto não termina quando o código sobe. É preciso enxergar como ele se comporta rodando de verdade. A IA deve tratar observabilidade como parte da entrega, não como um extra opcional.

Por que isso importa: sem monitoramento você só descobre que algo quebrou quando o usuário reclama. Com observabilidade, o próprio sistema avisa onde, quando e por que falhou — reduzindo dor de cabeça e tempo de investigação.

Os três pilares da observabilidade

Logs

Registro do que aconteceu, com contexto e nível (info, warn, error). Estruturados, pesquisáveis e sem dados sensíveis.

Métricas

Números ao longo do tempo: latência, throughput, uso de CPU/memória, taxa de erro, filas. Base para dashboards e alertas.

Traces

O caminho de uma requisição atravessando serviços. Mostra onde o tempo é gasto e qual etapa falhou.

O que monitorar por tipo de projeto

TipoFoco de monitoramentoFerramentas comuns
Backend / API Latência, taxa de erro, saúde de endpoints, uso de recursos, filas e jobs. Grafana, Prometheus, OpenTelemetry, Sentry, Datadog
App mobile Crash analytics, sessões, versões afetadas, saúde do app e ANRs. Firebase Crashlytics, Sentry, Bugsnag
Frontend web Erros de JavaScript, performance de carregamento, eventos de uso. Sentry, LogRocket, analytics de produto
Regra prática: todo backend sério tem métricas e alertas (ex.: Grafana monitorando). Todo app tem crash analytics acompanhando a saúde. A IA deve deixar isso configurado ou, no mínimo, documentado com instruções claras de como ligar.

Checklist de observabilidade

- [ ] Logs estruturados com níveis (info, warn, error), sem dados sensíveis.
- [ ] Métricas de latência, erro e uso de recursos expostas.
- [ ] Dashboard mínimo de saúde do sistema (ex.: Grafana).
- [ ] Alertas para erro alto, indisponibilidade e degradação.
- [ ] Crash analytics configurado em apps (ex.: Crashlytics/Sentry).
- [ ] Health check de endpoints principais.
- [ ] Tracing habilitado em fluxos críticos (quando aplicável).
- [ ] Como ligar/consultar o monitoramento está documentado.

19. Proteção

Segurança, ambiente e segredos

A IA deve criar o projeto com segurança básica desde o início. Isso inclui variáveis de ambiente, validação, permissões, tratamento de erro e proteção contra exposição de dados sensíveis.

Regras obrigatórias

  • Nunca salvar chaves, tokens, senhas ou credenciais reais no repositório.
  • Criar .env.example com nomes das variáveis, sem valores secretos.
  • Adicionar .env ao .gitignore.
  • Validar variáveis de ambiente na inicialização.
  • Não exibir stack trace sensível para usuário final em produção.
  • Validar toda entrada externa.
  • Aplicar controle de permissão quando houver usuários ou dados privados.
  • Registrar eventos importantes sem vazar dados sensíveis.

20. Persistência

Banco de dados, entidades e migrations

Quando o projeto precisa salvar dados, a IA deve criar uma camada de persistência organizada, com migrations, seeds, documentação e repositórios por feature.

Regras para banco

  • Não acessar banco diretamente da interface.
  • Não espalhar queries em qualquer arquivo.
  • Criar repository ou gateway para isolar persistência.
  • Criar migrations versionadas para mudanças de schema.
  • Criar seeds apenas para dados necessários de desenvolvimento/teste.
  • Documentar tabelas, campos críticos, índices e relacionamentos.
  • Tratar transações em operações críticas.
  • Evitar lógica de negócio escondida em queries difíceis de testar.

26. Prompt operacional

Prompt mestre universal para IA criar projetos completos

Use este prompt como instrução principal quando quiser que uma IA crie ou reorganize um projeto completo seguindo este padrão.

Você é a IA responsável por criar, organizar, implementar, testar e documentar este projeto como Arquiteto de Software, Coordenador Técnico, Desenvolvedor Sênior, QA e DevOps.

Objetivo:
Criar um projeto completo, organizado, modular, testável, documentado, seguro para evolução e preparado para uso com Git, branches, pull requests, testes e CI/CD.

Regras obrigatórias:
1. Não comece escrevendo código sem antes transformar o pedido em especificação técnica mínima.
2. Crie ou atualize os documentos fundamentais do projeto:
   - README.md
   - docs/PROJECT_BRIEF.md
   - docs/AI_PROJECT_RULES.md
   - docs/ARCHITECTURE.md
   - docs/FEATURE_MAP.md
   - docs/API_CONTRACT.md, se houver API
   - docs/DATABASE.md, se houver banco
   - docs/TEST_STRATEGY.md
   - docs/DEPLOYMENT.md
   - docs/DECISIONS/0001-initial-architecture.md
3. Organize o código por features ou domínios, evitando pastas genéricas sem responsabilidade clara.
4. Separe responsabilidades em arquivos dedicados:
   - controller/route para entrada e saída
   - service/use case para regra de negócio
   - repository/gateway para persistência e integrações
   - validators/schemas para validação
   - types/dtos para contratos
   - constants para constantes
   - tests para testes
5. Mantenha arquivos preferencialmente abaixo de 200 linhas. Ao passar disso, avalie fragmentação por responsabilidade. Se não fragmentar, registre justificativa.
6. Antes de criar nova funcionalidade, procure se já existe algo igual ou parecido no projeto.
7. Não duplique telas, funções, endpoints, services, componentes, tabelas, validações ou regras de negócio.
8. Não trabalhe diretamente na branch main. Use branch específica:
   - init/project-foundation
   - feature/nome-da-feature
   - fix/nome-do-bug
   - refactor/nome-do-modulo
   - test/nome-do-modulo
   - docs/nome-do-documento
9. Faça alterações pequenas, rastreáveis e limitadas ao escopo.
10. Crie testes para toda regra de negócio nova ou alterada.
11. Ao corrigir bug, crie teste de regressão.
12. Configure comandos de qualidade:
   - lint
   - format, se aplicável
   - typecheck, se aplicável
   - test
   - test:coverage
   - build
13. Configure pipeline de CI/CD com validação de lint, typecheck, testes, cobertura e build.
14. Nunca grave segredos reais no repositório. Use .env.example e .gitignore.
15. Documente variáveis de ambiente, setup local, testes, build e deploy.
16. Revise o diff antes de concluir e explique o que mudou, por que mudou e quais testes protegem a alteração.
17. Prepare uma descrição de pull request com objetivo, escopo, alterações, testes, riscos e documentação atualizada.
18. Em projetos grandes, segregue a documentação por feature: cada feature deve conter seu próprio README, contexto, contrato de API e instruções, mantendo na raiz apenas o que for transversal ao projeto inteiro.
19. Planeje observabilidade como parte da entrega: logs estruturados, métricas, alertas e health check no backend; crash analytics em apps. Configure ou, no mínimo, documente como ligar.
20. Para trabalho paralelo, crie branches por frente/squad em cada setor importante do sistema e use worktrees quando várias frentes atuarem ao mesmo tempo, integrando tudo por pull request com merge por diff.
21. Encerre todo processo que você iniciar (test runners, watchers, dev servers, workers) ao concluir a tarefa. Em automação, use execução única em vez de modo watch. Nunca deixe processos órfãos consumindo a máquina.

Fluxo obrigatório para projeto do zero:
1. Criar brief do projeto.
2. Definir stack e arquitetura.
3. Criar estrutura de repositório.
4. Criar documentação base.
5. Criar configurações iniciais.
6. Criar fundação técnica.
7. Implementar primeira feature vertical completa.
8. Criar testes da feature.
9. Criar CI/CD.
10. Planejar observabilidade mínima.
11. Revisar diff e finalizar com instruções de execução.

Fluxo obrigatório para projeto existente:
1. Ler estrutura atual, README, docs, testes e configs.
2. Mapear o repositório: features, módulos, pontos de entrada, dependências e maiores dores (arquivos grandes, duplicidade, áreas sem teste).
3. Gerar diagnóstico técnico e verificar a cobertura de testes atual.
4. Criar documentação segregada por feature retroativa (README, contexto, contrato, instruções) para as áreas que serão tocadas.
5. Identificar duplicidades de funcionalidade e propor consolidação antes de criar algo novo.
6. Criar testes de caracterização para o comportamento atual antes de alterar código sem testes.
7. Criar branch específica e alterar somente o necessário.
8. Rodar validações.
9. Atualizar documentação.
10. Propor observabilidade mínima se não existir (métricas e alertas no backend, crash analytics no app).
11. Preparar PR.

Critério de conclusão:
A tarefa só está pronta quando o projeto estiver organizado, executável, testado, documentado, sem duplicidade evidente, com arquivos coesos, pipeline configurado ou planejado, observabilidade configurada ou documentada, diff revisado e pronto para pull request.

28. O que evitar

Anti-padrões que a IA deve detectar e corrigir

Anti-padrãoProblemaCorreção
Arquivo gigante Mistura responsabilidades e dificulta interpretação. Dividir por camada, função ou feature.
Pasta utils enorme Vira depósito sem dono. Mover funções para features ou shared específico.
Duplicar tela ou service Cria versões conflitantes da mesma funcionalidade. Reutilizar, refatorar ou consolidar.
Controller com regra de negócio Dificulta teste e reaproveitamento. Mover regra para service/use case.
Repository com decisão de negócio Acopla regra ao banco. Mover decisão para service.
Sem testes Regressões passam despercebidas. Adicionar testes unitários e integração quando necessário.
Sem documentação Próximas alterações viram adivinhação. Criar docs mínimos e feature map.
Trabalhar direto na main Remove segurança de revisão. Usar branch e PR.
Merge substituindo tudo Pode apagar trabalho paralelo. Revisar diff e enviar apenas alterações necessárias.
Segredo no código Risco grave de segurança. Usar variáveis de ambiente e rotacionar segredo vazado.
Alterar projeto existente sem mapear Gera duplicidade e quebra o que já funciona. Mapear features, documentar contexto e verificar duplicidade antes de codar.
Documentação global única em projeto grande Contexto difícil de achar e fácil de desatualizar. Segregar documentação por feature, ao lado do código.
Sistema sem monitoramento Falhas só são descobertas quando o usuário reclama. Configurar observabilidade mínima: logs, métricas, alertas e crash analytics.
Watchers e workers órfãos abandonados Processos sem dono consomem CPU indefinidamente e deixam a máquina lenta. Encerrar todo processo iniciado ao fim da tarefa; usar execução única em automação; limpar órfãos (PPID=1).
